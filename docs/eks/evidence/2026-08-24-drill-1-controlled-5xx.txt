1. THE HTTP COLUMN FLIPS BACK TO 200 AT 15:22:20Z, four minutes before the alert fired, and that was

   THE ALERT STILL FIRED LEGITIMATELY, and the reason is worth understanding rather than glossing:
   VoteballHighErrorRate reads a 5-MINUTE rate window, so the error ratio stays elevated for minutes
   after the errors themselves stop. The outage ran 15:18:09Z-15:22:03Z (~4 minutes), the expression
   went true at 15:20:02Z, and `for: 5m` elapsed at 15:24:55Z with the window still carrying the
   outage's errors. So the alert fired on real, recorded errors -- but on their tail, not on a
   still-broken site.

   What this run therefore does NOT prove is the steady-state case where the break outlasts the
   alert. Nothing here is falsified; the evidence is just narrower than intended.

2. THE `HEALTH` COLUMN READS 404, NOT 200, AND THE CLOSING LINE ABOVE IS WRONG ABOUT WHY.
   `/health` is not reachable over the public hostname at all: nginx proxies only `/api/*`, so
   https://<app_domain>/health is a 404 from the frontend and never reaches the backend. It is the
   IN-CLUSTER probe target -- which is exactly why scripts/ci/smoke-test.sh deliberately does not
   test it either.

   The underlying claim is still true and still matters -- the liveness probe does not depend on RDS,
   which is what stops a database outage from restarting every pod -- but this column was never
   measuring it. Proving that needs a probe from inside the cluster
   (`kubectl exec <backend-pod> -- curl localhost:5000/health`), which is what the script now does.
   The 404s above are the drill measuring the wrong thing, recorded rather than quietly dropped.

The chain: a commit pushed to master earlier in this session went through application-ci, which
triggered application-cd, which promoted to the `release` branch and ran `argocd app sync` at
15:22:40Z. That sync restored every object in the chart -- including the NetworkPolicy this drill had
deliberately deleted three minutes earlier.

WHY THE DRILL'S OWN PRECAUTION DID NOT HELP, which is the part worth keeping:

This script suspends `syncPolicy.automated` before breaking anything, precisely so selfHeal cannot
undo the break before the alert fires. That is necessary and NOT SUFFICIENT. `syncPolicy.automated`
governs only ArgoCD's own automatic reconciliation. An explicit `argocd app sync` -- which is exactly
what Jenkinsfile-cd's Deploy stage issues, authenticated as `jenkins-cd` -- goes through regardless.
Suspending auto-sync buys protection from the controller and none at all from the pipeline.

So a chaos drill in `devops-app` is safe from ArgoCD only while NO CD DEPLOY IS IN FLIGHT, and CI is
triggered by any push to master -- including the pushes that carry the drill's own scripts and
evidence. The mechanism that ended this drill was the drill's own repository activity.

WHAT THAT MEANS FOR THE RESULT ABOVE: unchanged. VoteballHighErrorRate still fired at 15:24:55Z on
real recorded errors, over a real ~3m54s outage (15:18:09Z -> 15:22:03Z). What is narrower than
intended is still narrower, and for the reason now correctly identified.

ONE UNPLANNED POSITIVE: this is evidence, not sought, that a hand-deleted NetworkPolicy in
devops-app is restored by the delivery system within about four minutes -- a property no drill in
this repository had previously demonstrated.
