RESULT: PASS, with one honest gap.
  - Agent pod killed mid-build -> build #70 ABORTED. Jenkins cleaned up; no orphan agent.
  - Website served 200 throughout (5 polls during the kill, plus after). CI failure never touches
    delivery of the running site -- which is the property this drill exists to show.

FINDING (metric families are NOT interchangeable):
  The `jenkins_*_value` family (bundled Metrics plugin) reads 0.0 for queue_size, queue_stuck,
  executor_count and node_online -- even with a build running. The `default_jenkins_builds_*` family
  (the prometheus plugin's own collector) carries 257 non-zero series with real data: build counts,
  durations, health scores, failed_build_count_total.

  Both readings are arguably CORRECT: with the Kubernetes cloud provisioning agents on demand, an
  executing build is not queued, so queue_size 0 is truthful, and no agent is connected between
  builds so node_online 0 is truthful too.

  BUT: JenkinsQueueStuck fires on `jenkins_queue_size_value > 0` for 15m, and this drill did NOT
  prove that metric can ever become non-zero on this cluster. Killing an agent aborts the build
  rather than queueing it. To fire that alert you must make agent PROVISIONING fail (so items pile
  up unscheduled), not kill an agent that already exists. That is a different drill and was not run.
  Status: the alert is semantically right and UNPROVEN, not disproven. Recorded rather than claimed.


SUPERSEDED IN PART (2026-08-18, same day): the gap recorded above -- that JenkinsQueueStuck was
unproven -- was closed by drill 5, see 2026-08-18-drill-5-jenkins-queue-stuck.txt. Blocking agent
PROVISIONING with a ResourceQuota (rather than killing an existing agent) drove
jenkins_queue_size_value to 2 and the alert to firing after its 15m threshold, then back to inactive
once the quota was removed. This file's reasoning about WHY killing an agent cannot produce that
condition stands and is the reason drill 5 was needed.
