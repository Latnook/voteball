# Moving environment identity out of the committed chart values (2026-09-08)

**Status: proposed, not implemented.** Written at the repo owner's request after they asked why
`charts/voteball/values.yaml` carries real Terraform outputs in a public repository.

## 1. The complaint is correct

`Latnook/voteball` is `PUBLIC` (verified, not assumed: `gh repo view --json visibility`). Nine fields
in the committed `charts/voteball/values.yaml` are this AWS account's identity:

| Field | Published value |
|---|---|
| `image.registry` | `<account-id>.dkr.ecr.il-central-1.amazonaws.com` |
| `config.DB_HOST` | the RDS endpoint hostname |
| `config.S3_BUCKET` | `voteball-rollups-<account-id>` |
| `config.SNS_TOPIC` | `arn:aws:sns:…:<account-id>:voteball-notifications` |
| `ingress.host` | `voteball.latnook.com` |
| `ingress.certificateArn` | ACM certificate ARN |
| `ingress.wafAclArn` | WAF web-ACL ARN |
| `backup.roleArn` | `arn:aws:iam::<account-id>:role/voteball-backup-irsa` |
| `worker.roleArn` | `arn:aws:iam::<account-id>:role/voteball-worker-irsa` |

The AWS account id appears seven times.

**None of this is a credential**, and the threat model should be stated honestly rather than
inflated: an account id is not a secret, the RDS endpoint resolves only inside an isolated subnet
with no NAT or IGW route, and an IRSA role ARN is unusable without a trust relationship that names
the cluster's own OIDC provider. Nothing here is directly exploitable.

What it is, is free reconnaissance published for no benefit — and the argument that has justified it
is weaker than it appears.

## 2. Why it is currently committed, and where that argument stops

ArgoCD renders the chart **from git**. It cannot read `terraform output`. Leaving these fields as
placeholders on the `release` branch means ArgoCD syncs placeholders over a working cluster — the
`ImagePullBackOff` failure recorded in `CLAUDE.md` and observed on the 2026-07-20 rebuild. So
*something* has to carry the values to ArgoCD, and today that something is the committed file.

**The gap in that reasoning: an ArgoCD `Application` can carry them, and it is never committed.**
`spec.source.helm.parameters` overrides chart values at render time. The Application for this repo is
generated by `scripts/render-argocd-app.sh` from `argocd/voteball-application.yaml.tmpl` and applied
with `kubectl` — the template is in git, the *rendered manifest is not*. That script already reads
Terraform (`tf_output`); it simply only uses it for `REPO_URL` today.

So the escape hatch exists and was not taken. That is the whole finding.

## 3. The ten fields do not split evenly, and the split is the design

**Stays in git — `image.tag` and the four `image.digests` entries.**

Not because of ArgoCD, but because **`scripts/ci/previous-tag.sh` recovers the rollback target by
reading `git log -p` over `values.yaml`.** The file's history *is* the deployment record, and
`application-cd`'s automatic rollback depends on it. Moving the tag into the Application would
replace a durable, reviewable git history with a mutable cluster object and delete rollback as a
side effect.

They also leak nothing. `image.tag` is a git SHA of a public repo, and a digest is a content address.

Note the digests are already **not** sync-managed: `promote-to-release.sh` writes them, and
`sync-values-from-tf.sh` cannot see them because its line matcher only matches two-space indent while
the digest map sits at four. That is documented in `values.yaml` as being by construction rather than
by exclusion list, and this change does not disturb it.

**Moves to the Application — the nine fields in section 1.** They are environment identity. Nothing
reads their history, nothing rolls back to a previous ACM ARN, and a fork needs different values
anyway.

## 4. Mechanism

`argocd/voteball-application.yaml.tmpl` gains a `helm.parameters` block in the `voteball`
Application's `source`, using the same `${VAR}` substitution the template already uses for
`${REPO_URL}`:

```yaml
  source:
    repoURL: ${REPO_URL}
    targetRevision: release
    path: charts/voteball
    helm:
      parameters:
        - {name: image.registry,          value: "${REGISTRY}"}
        - {name: config.DB_HOST,          value: "${DB_HOST}"}
        - {name: config.S3_BUCKET,        value: "${S3_BUCKET}"}
        - {name: config.SNS_TOPIC,        value: "${SNS_TOPIC}"}
        - {name: ingress.host,            value: "${APP_DOMAIN}"}
        - {name: ingress.certificateArn,  value: "${CERT_ARN}"}
        - {name: ingress.wafAclArn,       value: "${WAF_ARN}"}
        - {name: backup.roleArn,          value: "${BACKUP_ROLE}"}
        - {name: worker.roleArn,          value: "${WORKER_ROLE}"}
```

`render-argocd-app.sh` fills them from `tf_output`, exactly as it fills `REPO_URL`. The committed
`values.yaml` returns to carrying placeholders for these nine, which is what its `FILLED-BY-SYNC`
header has always claimed and has never been true.

### Files this touches

| File | Change |
|---|---|
| `argocd/voteball-application.yaml.tmpl` | the block above |
| `scripts/render-argocd-app.sh` | export nine more `tf_output` values before substitution |
| `scripts/sync-values-from-tf.sh` | `managed` drops from ten entries to one (`image.tag`) |
| `scripts/tests/test-sync-values.sh` | drop the eight cases for removed fields; **keep** the unquoted-tag regression case, which guards `previous-tag.sh` |
| `charts/voteball/values.yaml` | nine values become placeholders; header comment rewritten |
| `CLAUDE.md`, `docs/deploy.md` | the "deliberate exception … not optional" passage is no longer true |

## 5. What this makes worse, stated plainly

- **A second place chart values can come from.** Today `values.yaml` is the single authoring path.
  Afterwards a reader must know that nine fields are overridden by the Application. Mitigated only by
  the placeholder values being obviously fake and the header saying where they come from.
- **`render-argocd-app.sh --check` becomes load-bearing for the app's config, not just its wiring.**
  It uses `kubectl diff` against the rendered template, so it already catches a parameter that drifts
  — but a *failure to render* now breaks the app rather than only its repo URL.
- **Applying the Application by hand without rendering is newly dangerous.** Today that yields the
  right values from git; afterwards it yields placeholders. The template's existing "Do NOT
  `kubectl apply` this file directly" warning becomes more serious and should say so.
- **Forking gets one more required step ordering**: `render-argocd-app.sh` must run before the
  Application is created, which `deploy.sh` step 11 already does.

## 6. What it does NOT fix

- The account id still appears in `terraform/backend.hcl` (gitignored), in evidence files under
  `docs/eks/evidence/` (dated records, deliberately never edited), and in this document's own table.
  **Anyone auditing exposure should grep the whole repo, not just `values.yaml`** — fixing the chart
  and declaring the account id private would be false.
- Nothing about secrets. Those are already in Secrets Manager and never in git; this pass concerns
  non-secret identity only.

## 7. Verification

1. `./scripts/render-argocd-app.sh --check` → clean.
2. `./scripts/sync-values-from-tf.sh --check` → passes with one managed field.
3. `scripts/tests/run-ci-suite.sh` → green.
4. `git show origin/release:charts/voteball/values.yaml` contains **no** account id — the real check,
   run against the branch ArgoCD actually deploys, not the working tree.
5. A **full destroy/deploy cycle**. This changes the ArgoCD bootstrap path, and the failure it risks
   is precisely the one `CLAUDE.md` records: placeholders reaching a live cluster. Nothing short of a
   rebuild exercises it — steps 1-4 all pass against an already-correct cluster.

## 8. Sequencing

**Do not start this while a teardown fix is unverified.** As of writing, `destroy.sh`'s
`--timeout=180s` namespace wait and its cluster-wide ExternalSecret sweep have not been through a
teardown. Changing the ArgoCD bootstrap path in the same window puts two variables into one
destroy/deploy cycle, and the deploy path is the one place that should carry a single change at a
time.

Order: verify the teardown fixes → implement this → verify with its own cycle.
