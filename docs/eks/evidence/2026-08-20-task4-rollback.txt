# Task 4 evidence -- deliberate broken deploy and automatic rollback (2026-08-20)

A DELIBERATELY BROKEN frontend image was built outside CI (CI would have refused it -- the failing
behaviour is intentional, not a test failure) and pushed under tag dead10c. That tag is valid hex
and passes CD's ^[0-9a-f]{7,40}$ input check, but is deliberately NOT any real commit in this
repository, so no genuine commit ends up with an image that misrepresents its contents. The other
three images were byte-identical copies of the 9a58532 images, retagged, so ONLY the frontend is bad.

The break: nginx.conf returns 500 on "/". The frontend's startupProbe targets "/" with a 30s budget
(failureThreshold 10 x periodSeconds 3), and a failing STARTUP probe kills the container -- so the
new pod never became Ready and crash-looped. Same mechanism as the 2026-08-17 demo, re-run on the
cluster rebuilt 2026-08-20 and, this time, through a CD pipeline that now also carries the
Monitoring Gate added by the Task 5 observability work.

## Why this recovery is slower than 2026-08-17's 2m08s -- both halves are deliberate

1. ~4m40s was spent waiting for ArgoCD to stop retrying a revision nobody wanted any more, and
   the apply itself then took 26 seconds. The detail matters, so here it is from the Application
   object and the argocd-application-controller log rather than from the pipeline's own narration:

     11:40:54  controller initiates AUTOMATED sync to f238f30 (the dead10c promote)
     11:40:55  application-cd #5's own `argocd app sync` is rejected: "another operation is already
               in progress". BENIGN -- it is auto-sync racing #5's own Promote commit, which is
               exactly what the pipeline's message says
     11:51:14  the f238f30 operation is still alive and failing: "Retrying operation. Attempt #1"
     11:52:13  application-cd #6's `argocd app sync` is rejected with the SAME error -- but this
               time the operation in flight is #5's DOOMED sync of dead10c, still retrying. The
               pipeline prints the same "auto-sync picked up the Promote commit first" message,
               which is accurate for #5 and MISLEADING for #6
     11:52:35  Attempt #3 -> Failed
     11:53:59  Attempt #4 -> Failed ("waiting for healthy state of ... and 28 more resources")
     11:56:49  Attempt #5 -> Failed
     11:56:53  the doomed operation is finally done; auto-sync immediately initiates a sync to
               a509871 (the rollback commit), startedAt 11:56:53Z
     11:57:19  finishedAt -- "successfully synced (no more tasks)". The apply took 26 SECONDS

   The Application's sync history confirms dead10c never landed once: id 4 is e7421e1, id 5 is
   a509871 at 11:57:19Z, and there is no entry in between. Verify with:
       kubectl get app voteball -n argocd -o json | jq '.status.history, .status.operationState'

   So the pipeline was not slow, and neither was the rollback: CD asked for the sync at 11:52:13 and
   was told to wait, then waited correctly. What the wait was FOR is the finding -- and it means the
   "auto-sync picked up the Promote commit first" message should not be read as proof of the benign
   case. It prints for both.
2. The Monitoring Gate ran with a 330-second settle wait -- 300s of recording-rule lookback plus one
   30s scrape interval. Jenkinsfile-cd sets GATE_SETTLE_SECONDS=330 only when the build IS a rollback
   (ROLLBACK_DEPTH > 0), because the SLI recording rules' 5-minute window still contains samples from
   the release being rolled back. Without the wait, a rollback would be judged on the broken
   release's error rate and fail itself. This demo is the first time that path has run for real.

## Visitor-visible impact: no error was ever served, one request timed out

2,561 probes of https://voteball.latnook.com/ at 2/s spanning 11:39:29Z -> 12:04:28Z -- the whole
demo, from before the broken deploy to after the recovery. (Counted from the committed poll file,
which is the thing a reader greps: `wc -l < 2026-08-20-task4-rollback-site-poll.txt`.)

  2,560 returned HTTP 200.
      1 returned 000 at 11:52:31Z -- curl's code for "no response", i.e. the request did not
        complete within the client's 5-second timeout. It is NOT an HTTP error returned by the
        site; no status code was ever received. It falls during the rollback sync (11:52:15-11:52:22
        applied the manifests server-side).

See 2026-08-20-task4-rollback-site-poll.txt; check it with:
    awk '$2!=200' docs/eks/evidence/2026-08-20-task4-rollback-site-poll.txt   # prints the one line

Prometheus, queried afterwards over the same window, recorded NO server-side error at all:
    sum(voteball:journey_errors:rate5m)              = 0   at 11:45, 11:50, 11:52:40, 11:55, 12:00, 12:04
    min_over_time(voteball:availability:ratio5m[30m]) = 1   evaluated at 12:05
(That ratio is trustworthy here precisely because the canary Deployment guarantees the denominator
is never empty -- see the canary note in CLAUDE.md.)

So the honest reading is: the site served no errors, and one client request out of 2,555 failed to
get any response within 5 seconds during the sync. Whether that was an ALB target re-registration or
a blip on the polling laptop cannot be determined from this evidence, and is not claimed either way.
The 2026-08-17 demo recorded 1,539/1,539 clean, so this is not a regression in the mechanism -- it is
one unexplained timeout, recorded rather than rounded away.

The structural reason the impact is this small is unchanged: a pod that never passes readiness is
never added to the Service's endpoints, and the old ReplicaSet is never scaled down because the
rollout never progresses. Contrast 2026-08-04's demo, where the backend returned 500 while PASSING
its probes -- ArgoCD called that Healthy and only the smoke test caught it, at a cost of ~3 minutes
of real errors. The three demos deliberately exercise different layers.
