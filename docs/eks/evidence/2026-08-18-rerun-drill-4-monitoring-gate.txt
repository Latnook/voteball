WHAT THIS DRILL IS FOR: proving the gate catches something nothing before it could. A release

  CD smoke test:   curl --max-time 15, checks for 200      -> PASSES
  Monitoring gate: GATE_MAX_P95_SECONDS=1.0                -> MUST FAIL (1.5 > 1.0)

This re-runs the drill first captured in 2026-08-18-drill-4-monitoring-gate.txt. It matters
because the gate's environment changed tonight: GATE_REQUESTS was raised 40->60, the SLI
recording rules were added, and the synthetic canary now supplies baseline traffic. A
regression in the gate would be invisible until a real bad release shipped.

--- IMPORTANT: rollback reverts the IMAGE TAG, not the SOURCE ---
  After the rollback, charts/voteball/values.yaml points at af4c5b5 and the running pods serve
  the fast code again -- but commit 443bd37 is still on master, so services/backend/app.py
  STILL CONTAINS THE 1.5s SLEEP. The next build from master would rebuild the slow code and
  ship it again, and this time no rollback would help because the 'previous' tag would also
  contain it eventually.

  This is inherent to how rollback is designed here (docs/design/2026-08-04-cicd-split-design.md
  section 8): rollback goes through git by re-pointing image.tag at a known-good SHA, precisely
  so Jenkins needs no cluster write permission. The trade-off is that it restores the RUNNING
  ARTEFACT, not the SOURCE. Reverting the bad commit is a separate, human step.

  It is worth saying out loud in an interview: 'automatic rollback bought me minutes to react,
  it did not fix the bug.' A rollback that also reverted source would be rewriting history from
  CI, which is a much worse property to have.
