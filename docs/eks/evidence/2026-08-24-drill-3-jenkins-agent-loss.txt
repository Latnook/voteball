  Verified by materialising that exact tree and re-running the same detection:

    $ (the test's own sed|grep over `find scripts services -name '*.sh'`)
      matches at 653b15d: 18
      scripts/tests/test-notify.sh -> matches at lines 43, 72, 81

  Also checked that it was not a grep-implementation difference: this workstation's `grep` is a shell
  function wrapping ugrep, so the same detection was re-run under /usr/bin/grep (GNU grep 3.12, which
  is what the python:3.12-slim CI container uses). Both give 18 and both match test-notify.sh.

  So the workspace #9 ran against was INCOMPLETE -- two of eighteen shell scripts were missing or
  truncated -- 1m51s after its predecessor's agent was force-deleted mid-build. #10, on the same
  commit range and a settled agent, scanned all of them and passed 21/21.

  WHAT TO TAKE FROM IT: an agent killed mid-build can cost more than its own build. The next build
  can fail on an assertion that does not reproduce anywhere, which reads as a real regression and
  sends someone hunting a defect that is not there. This repository has no `ws-cleanup`, so a
  half-populated workspace is not swept before reuse.

  This is exactly the class of failure the drill is supposed to surface, and it was surfaced by
  accident rather than by design. It is recorded here rather than quietly re-run into a green build.

=== NOTE ON THE BROKEN BLOCK ABOVE ===

  The script's own AFTER section died with a JSONDecodeError. The cause is curl, not Jenkins: the
  tree query `builds[number,result,building]{0,4}` contains `{0,4}`, and curl treats `{}` as a glob
  set unless given -g/--globoff. The request never reached Jenkins in the form intended and the empty
  body was fed to json.load. The script now passes -g.

=== CORRECTION: THIS DRILL DID NOT START THE BUILD IT KILLED ===

Read line 10 of this file again:

  application-ci triggered (HTTP 403); last build before was #8

HTTP 403 is a failure. The script printed it inside a line that says "triggered" and carried on, so
the transcript reads as though the drill started a build and then killed its agent. It did not.

The cause is Jenkins CSRF: the crumb is bound to the SESSION that issued it, and the script fetched a
crumb with one curl invocation and POSTed with another, discarding the cookie in between. Reproduced
afterwards against the same controller:

  crumb without the session cookie -> HTTP 403
  crumb with    the session cookie -> HTTP 201

So what actually happened is that build #8 was ALREADY RUNNING -- started 15:27:06Z by a push earlier
in this session -- and the drill's "wait for an agent pod" loop found #8's agent and killed that.

WHAT SURVIVES, AND WHAT DOES NOT:

  SURVIVES. An agent was force-deleted mid-build. The site held 200 on every poll for five minutes,
  Jenkins provisioned a replacement agent on its own at 15:30:52Z, and the interrupted build went
  ABORTED rather than hanging. Those are the properties the drill exists to demonstrate and they were
  demonstrated -- the ownership of the build does not change what happened to it.

  DOES NOT SURVIVE. The claim that this was a controlled, self-contained drill. It killed a build it
  did not start, and it did so only because one happened to be running. Had the queue been empty, the
  script would have waited its 300s and exited 1 -- or worse, on a busy controller, killed a build
  doing something someone cared about.

The script now fails loudly when the trigger does not return 201, rather than printing the code and
continuing. A drill that measures whatever it finds lying around is not a drill.

This is the second time today a script here reported a number it had not measured -- the first was
the HEALTH column in drill 1. Both had the same shape: a command failed, its exit status was folded
into a string, and the transcript looked complete.
